# 技术路线

一句话：**被动识别**——抓到你自己网络里的流量，解密、读出每台设备查了哪些域名、连了哪些服务器，再归到应用，估计流量和使用时长。只在自己的网络里做，只读，不看 TLS 内容。

## 1. 需求与两条路线

原始需求：看家里每台设备访问了哪些网站和应用、流量多少、用了多久。路由器是黑盒，改不了。

| | 路线 A：自己的网关 | 路线 B：监听空口 |
|---|---|---|
| 做法 | 在黑盒路由器后面接一台自己的路由器 / 小主机当网关，设备改连它 | 监听网卡抓空口里加密的 802.11 帧，自己解密 |
| 抓到什么 | 明文 IP 包，不用解 802.11 | 加密帧，必须有口令和设备连入时的握手 |
| 覆盖 | 只有迁过来的设备，信息最全 | 监听网卡听得到的那个信道上的全部设备，不用改任何设备 |
| 硬件 | 一台能刷 OpenWrt 的路由器或小主机 | 一张支持监听模式的 USB 网卡，加一台 Linux 机器 |
| 软件入口 | `python3 -m wifi80211.report 网关抓包.pcap` | `python3 -m wifi80211.report 抓包.pcap --keys 密钥文件` |

两条路线最终都落到同一套分析：事件 → 归应用 → 报告，所以软件只做一遍。

现成的开源工具（ntopng + nDPI、Zeek、AdGuard Home）能做路线 A 的大部分，我们没有重复造它们；我们用 nDPI 当第二个标准答案（见 §4）。nDPI 不认识国内应用（抖音、快手、哔哩哔哩等只说 TLS），我们的规则补上这一块。

## 2. 数据流

```
抓包文件（pcap / pcapng，可以是 .gz）
  capture / radiotap / frames / parser     读文件、拆 radiotap、解 MAC 头
  handshake / ft / groupkeys / tdls        从握手推出 PTK、GTK（也可以直接给 TK）
  crypto / decrypt / pipeline              CCMP / GCMP / TKIP / WEP 解密，A-MSDU 拆开
  plain                                    以太网 / Linux cooked 的明文抓包（路线 A）
  net / dns / tcpstream / tls / quic       IP / UDP / TCP → DNS、TCP 重组、TLS ClientHello、QUIC Initial
  activity / traffic                       按设备（MAC）汇总成事件、逐流的包数和字节
  apps + rules/*.json                      域名归到应用，估计使用时长
  report                                   一条命令输出表格 / json / csv
```

## 3. 关键技术选择

- **自己实现每一层**：只依赖标准库加 pycryptodome（AES），不依赖 Wireshark 或 aircrack。既是协议学习，也让每一层都能单独验证。在 Mac 自带的 Python 3.9 上直接就能跑。
- **解密靠握手**：口令加 SSID 得到 PMK，再结合握手里的随机数推出 PTK。没抓到握手但有 TK 时可以直接给 TK。
- **WPA3-SAE 做不到被动解密**：即使知道口令也不行（PMK 依赖双方的私有随机数）。家里路由器要用 WPA2 或 WPA2/WPA3 混合模式。
- **识别靠三条证据**：DNS 明文查询、TLS / QUIC 的 SNI、DNS 应答里的 IP 到域名映射（没有 SNI 时补名字）。明文 HTTP 的 Host 也读。
- **域名归应用靠公开清单**：规则不手写，由 `tools/build_app_rules.py` 从 v2fly/domain-list-community（MIT）固定提交生成，记录来源和 sha256；你自己的规则优先；5 家公开 DoH/DoT 服务单独标「加密 DNS」。
- **使用时长是估计**：相邻活动不超过一个间隔算一段，不是屏幕时间。

## 4. 验证方法（项目最重要的部分）

- **tshark 当标准答案**：24 个 Wireshark 公开样例上逐字段、逐字节对照；已知差异固定成精确数字，变好或变坏都让测试失败。Wireshark 公布的 21 个 TK、20 个 GTK 全部推出。
- **不依赖 tshark 的自证**：握手 MIC、AES 密钥包装、IP / UDP / TCP 校验和——解密错一个比特就对不上。
- **没有样例的部分**：用公开向量（RFC 8448、RFC 9001）和独立构造器造包再对照 tshark；端到端测试造了一个 CCMP 加密的 802.11 抓包（DNS、TLS、HTTP、QUIC），只给一把 TK，读出的域名与 tshark 一致。
- **nDPI 交叉对照**：46 个名字 × TLS / QUIC / HTTP 共 138 条流，两边都按域名认应用，说法冲突 0 条。
- **变异检查**：每个新测试都故意改坏代码看能不能抓住，没抓住的补用例，剩下的写明为什么等价。

## 5. 已知限制

- 用口令解密必须抓到设备连入时的握手；设备已经连着就只抓到后面的数据，只能直接给 TK。
- 单网卡单信道：一张网卡同一时刻只听一个信道。
- 看不到的：ECH、非公开的 DoH 服务器、加密之后的内容。
- 做不到：SAE / OWE 的 PMK 推导、BIGTK 保护的信标、wpa-mlo-ccmp 的数据帧、Mesh 的 AMPE。
- TLS 和 QUIC 在真实流量上尚未验证（样例里没有这类流）；域名归属偏粗（腾讯、Google、Apple、Microsoft 是整家公司的归类），使用时长只是估计。
- **Mac 内置网卡监听**：README 记录了在这台 Apple Silicon Mac 上的实测，`tcpdump -I -i en0` 收到 0 个帧；其它机型有成功也有失败的报告，所以监听抓包按 Linux 机器计划。Mac 用来运行分析和看报告。

## 6. 日志与排错

每次运行默认在当前目录写 `wifi80211-时间.log`（DEBUG 级别，带运行头），出错时屏幕告诉你路径；密钥从不进日志。`--redact` 把 MAC、IP、域名换成短标记，发给别人之前用。规范见 `docs/日志规范.md`。

## 7. 开发方式

按依赖拆成互不相交的模块并行做：每个并行任务用一个 `git worktree`，我合并并解决 `tests/run_all.sh` 里的冲突。教训：带合并提交的历史上不要 `git rebase`。

## 8. 路线图

1. 买监听网卡（推荐 MT7921AU 系，下单前核对芯片和内核版本）和一台 Linux 机器；先让一台自己的设备断开重连，再开始抓包。
2. 用真实数据验证 TLS 和 QUIC，补自己的规则（`apps.unmatched` 会列出没规则的常见域名）。
3. 需要应用级、流量级的完整统计时，再做路线 A：一台自己的网关，抓包后用同一条命令分析。

进度、数字和每一步怎么验证的，见 `docs/wifi_scan_sim_roadmap_v3.md`。
