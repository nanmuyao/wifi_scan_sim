# 路线 B 实施方案：监听网卡 + Mac 上的 Linux 虚拟机

当前主线。前提：这是自己的家庭网络，口令已知，不改路由器、不连任何设备，只旁听。软件部分（解析、握手、解密、识别域名、归应用、报告）已经做完并用公开样本验证过；这份文档写的是**怎么拿到第一份真实数据，以及怎么判断这一步成没成**。

写法约定：**已核实**的写来源，**未核实**的写成待验证项并给出通过标准，不当作事实。

## 1. 先确认网络（买任何东西之前）

在 Mac 上读当前连接的网络信息（只读）：

```bash
system_profiler SPAirPortDataType | sed -n '/Current Network Information:/,/Other Local Wi-Fi Networks:/p'
```

要看三项：

| 项 | 要求 | 不满足怎么办 |
|---|---|---|
| Security | WPA2 Personal（或 WPA2/WPA3 混合） | 纯 WPA3（SAE）被动抓包解不开，这条路走不通 |
| Channel | 记下频段和信道，例：5 GHz 信道 44，80 MHz | 网卡必须支持该频段；信道若是 DFS 信道（52–144）可能被路由器自己换走 |
| 链路速率与 PHY | 例：802.11ac，80 MHz 下 866 Mb/s | 决定网卡需要几路天线，见 §2 |

注意：混合模式下，手机可能走 WPA3，那样那台设备解不开；抓包后用报告里的握手状态确认。

## 2. 买什么

### 2.1 网卡的硬性条件

1. **Linux 内核自带驱动，监听模式可用**（不要选要自己编译第三方驱动的型号）。
2. **支持路由器所在的频段**。5 GHz 信道意味着 2.4 GHz 单频的卡（如 AR9271）不能用。
3. **能收路由器用的信道宽度**（例：80 MHz）。
4. **天线路数不少于路由器和手机之间的空间流数（2×2）。**
   - 依据：80 MHz 的 802.11ac，一路空间流最高 433 Mb/s，二路 866 Mb/s；链路显示 866 Mb/s，说明路由器对这台设备用了两路空间流。
   - 推断（**待验证**）：只有一路接收的网卡（1×1）收不全两路空间流的帧，下行的大部分数据会缺失，而下行正好是看视频的主要流量。来源没有直接证实，要靠实测：同一时间同一信道，1×1 与 2×2 的卡各抓一次，比较收到的帧数。买之前宁可选 2×2。

### 2.2 候选（只列已查到的；其余待核实）

| 芯片 | 路数 | 已查到的 | 待核实 |
|---|---|---|---|
| MT7612U（AC） | 2T2R | 主线内核 mt76 驱动列为支持，监听模式和注入标为支持 [TechInfoDepot](https://techinfodepot.shoutwiki.com/wiki/TechInfoDepot:Linux_driver/mt76)；旧的第三方驱动没有监听代码路径，不要用 | 80 MHz 监听收包的实测、具体网卡型号 |
| MT7921AU（AX） | 2T2R | 列为 mt76 支持的芯片；内核 Kconfig 写明 2x2；Kismet 文档称支持 5 GHz 最高 80 MHz | 论坛反馈不一致：有人称 6.15 内核监听正常、更新的内核不行，另有 tx 超时、探测失败的报告（论坛与问题单，非官方）。没验证过 80 MHz 下收全数据帧。内核风险比 MT7612U 大，仅在买不到 MT7612U 时考虑 |
| MT7610U（AC） | 1T1R | 见上 | 按 §2.1 第 4 条不选 |
| AR9271 | 1T1R | 仅 2.4 GHz | 不选（频段不符） |
| RTL8812AU | — | 通常要第三方驱动 | 不选 |

买之前要再核对一次：具体型号用的是哪颗芯片（同一品牌常有换芯片的改版）、当前内核里的驱动状态。

### 2.2.1 购买与到手验收（预算约 500 元，2026-11-01 查到的）

- 首选 MT7612U。**认 USB ID `0e8d:7612`，不认品牌、型号或 "AC1200" 这类宣传词**：商品页或卖家要能给出 USB ID，否则按可退换处理。查到的资料里有一篇把型号和芯片对应写混了，不能当依据。
- 没有找到来源直接证实 MT7612U 在 80 MHz 下做监听抓包，**这一条仍是未验证项**，由下面的验收来判定。
- 另有 2026 年的 mac80211 补丁（v2，是否已合入未确认）提到：监听口与普通联网口并存时，mt76 注入的帧发不出去。本项目只抓包不注入，影响不大；仍建议把网卡整个直通给虚拟机，只用监听模式。

到手后按顺序验收，任何一步不过就停下来记录现象：

1. `lsusb` 的 USB ID 是 `0e8d:7612`；`dmesg` 里加载的是 `mt76x2u`，没有固件加载失败。
2. `iw list`：监听模式在 "Supported interface modes" 里；5 GHz 频段下列出 80 MHz 的信道宽度；两路天线（`Available Antennas` 为 TX/RX 都是 0x3）。
3. `tools/capture_monitor.sh -i IF -c 信道 --width 80 --duration 30` 抓 30 秒，退出后网卡能恢复联网。
4. 用 `python3 -m wifi80211.report` 看「抓包质量」：收到的是 5 GHz 80 MHz 的数据帧，序号缺口比例记下来。
5. 此时才对照 §4 的验收标准；1×1 与 2×2 对比实验（§2.1 第 4 条）有第二张卡时再做。

Apple Silicon 上 USB 直通是最大的未知项：先用这张卡试，直通失败就改用树莓派（§5）。

### 2.3 抓包机：Mac 上的 Linux 虚拟机

Mac 自带的 WiFi 监听抓不到包（README 有实测），所以抓包在 Linux 里做，分析仍在 Mac 上跑。

- 做法：虚拟机软件把 USB 网卡整个直通给 Linux 来宾，来宾内核直接驱动它，监听模式在来宾里生效。
- 软件候选：UTM、VMware Fusion、Parallels；**对 USB WiFi 网卡直通的实际支持，在 Apple Silicon 上都未核实**。苹果自带的虚拟化框架对 USB 直通有限，不要选它做后端。
- 来宾：ARM 架构的 Ubuntu 一类，内核 ≥ 5.18。
- 还需要：USB-C 转 USB-A 转接头（多数网卡是 USB-A）。
- 退路：树莓派装 Linux，不经过虚拟化，抓完把文件复制到 Mac。

## 3. 操作流程

1. Linux 来宾里确认网卡被识别、支持监听：`iw list | grep -A 12 "Supported interface modes"`。
2. 运行抓包脚本（`tools/capture_monitor.sh`，见 §6）：停掉网络管理、进监听模式、锁定信道和宽度、开始抓包并滚动切文件。
3. 抓包开始后，**让要观察的设备把 WiFi 关掉再打开一次**。这一步产生四次握手。
4. 正常使用设备（例：刷一段短视频，再放着不动），抓几分钟。
5. 停止，把文件拷到 Mac。
6. 写密钥文件（口令和 WiFi 名，只留在自己的电脑上，不进仓库），运行：
   `python3 -m wifi80211.report 抓包.pcap --keys 密钥文件`
7. 看报告里的「抓包质量」（见 §6）判断这一次抓得好不好，再看域名和流量。

## 4. 验收标准（拿到第一份真实数据后逐条判定）

数值是**初定**，拿到数据后允许调整，调整时要记录依据。

| # | 判定项 | 通过标准 | 不通过时先查 |
|---|---|---|---|
| 1 | 目标设备的握手 | 报告里该设备握手状态为 verified | 没抓到握手：让设备重连；口令或 WiFi 名写错 |
| 2 | 解密比例 | 目标设备的受保护数据帧里，解开的占 ≥ 90% | 握手之前的帧解不开属正常；其余看 #3 |
| 3 | 丢帧估计 | 由序号缺口估计的丢帧率 ≤ 5% | 网卡路数不足、虚拟机 USB 直通丢包、距离太远 |
| 4 | 域名 | 刷已知的网站或应用时，对应域名出现在报告里 | TCP 缺口丢了 ClientHello；DNS 被加密 |
| 5 | 与参照核对 | 同一时间手机上的应用与报告的应用一致 | 域名归属偏粗、规则缺失 |

## 5. 风险与退路

| 风险 | 表现 | 退路 |
|---|---|---|
| 虚拟机 USB 直通丢包或掉线 | #3 不过；抓包中途网卡消失 | 换 VMware / Parallels；仍不行用树莓派 |
| 网卡路数不足 | 下行帧缺失，#2 / #3 不过 | 换 2×2 的卡 |
| 手机走了 WPA3 | 该设备握手状态不是 verified | 无解（纯被动不可行）；只对 WPA2 设备做 |
| 设备在 2.4 GHz | 听不到 | 另开一张卡或换信道抓 |
| 设备漫游到别的信道 | 抓到一半没了 | 固定设备的频段，或多卡 |
| 抓包量太大 | 磁盘涨得快 | 按时间滚动切文件，只留需要的 |

## 6. 软件侧：已就绪与待做

已就绪（公开样本上验证过）：802.11 解析、握手与密钥推导、CCMP / GCMP / TKIP 解密、DNS / TLS / HTTP / QUIC 识别、归应用、流量与时长、报告、日志与解密失败诊断。

为这一步新增（见路线图）：

1. **抓包质量**（已完成，`wifi80211/health.py`）：每台设备的受保护帧数、解开数、握手状态与下一步、序号缺口估计的丢帧率、重传占比；解密成功时也显示，不只在全部失败时。报告表格有「抓包质量」一节，json 有 `health`，读法见 `docs/日志规范.md`。
   验证过的：24 个样例的序号计数器逐个和 tshark 字段的独立重算一致；在 wpa-Induction 上随机删掉一个计数器 5% / 10% / 20% 的帧，缺口数每次都正好多出删掉的个数；合成流在 5% / 10% / 20% 丢帧下估计与真实相差不到 0.2 个百分点。
   **没验证的**：缺口等于「物理上没收到」这一点只在构造数据上成立；QoS 单播计数器的分法样例给不出证据（没有一个 AP 持续向多台设备发 QoS 数据），靠标准、mac80211 的做法和自动选择；提醒用的 5% 丢帧、30% 重传是初定，缺口上限 64 是取的，都要等真实数据再调。
2. **A-MSDU 检查（已做，结论：没有问题）**：802.11ac 下行常把多个包聚合成一个帧。用独立加密方造的 CCMP 加密 A-MSDU，只给一把 TK，让 tshark 同样解密后逐帧对照：
   IP 包个数、地址、长度、域名事件、整条链的上下行字节都相同（下行 5803 字节、上行 492 字节与 tshark 精确相等），解密后的路径会正确拆开，视频流量不会漏。
   帧体不合法的 A-MSDU 原先被悄悄吞掉，现在 `decrypt_capture` 会在日志里报 WARNING 并在 `stats["amsdu"]` 里给出个数。测试：`tests/oracle/test_amsdu_decrypted_diff.py`。
3. **抓包脚本** `tools/capture_monitor.sh`（已完成）：只让网络管理忽略这一张网卡、监听模式、锁信道和宽度、滚动抓包、退出时恢复网卡；带 `--dry-run`。命令格式对照 `iw` 6.7 和 NetworkManager 手册，退出时恢复网卡的流程（正常、切监听失败、锁信道失败、Ctrl-C）用假命令测过，**没有在真实网卡上跑过**。
4. **短视频判断**（机制已完成，门槛未标定）：`wifi80211/streaming.py` 把每条流的下行按 5 秒一格累计，找出「持续下行」的时段（速率不低于门槛、活跃格之间空着不超过 15 秒连成一段、至少 30 秒），报告里按设备、按应用列出；格子数据在 24 个样例上与 tshark 逐格一致。输出叫「持续下行」，不叫「在刷短视频」：下载、直播也是这个形状。三个默认值（50 KB/秒、30 秒、15 秒）是第一次的猜测，**要等真实抓包（刷视频、看直播、发消息、放着不动各一段）才能标定**；**域名角色（视频 CDN / 接口 / 直播）不凭名字猜**，同样要有真实抓包再定。

### 第一份真实的刷视频数据（Mac 浏览器刷抖音网页版，用来校准「持续下行」）

条件：Mac 上用浏览器打开抖音网页版，约 3 分钟连续往下刷，然后关掉标签页放着约 2 分钟；`tcpdump` 抓 `en0`（明文，不涉及 802.11），共 63990 个包，内核丢包 0。**这不是手机应用的流量，也不是路线 B 的空口抓包**，只能说明机制在真实数据上的表现，不能直接定手机上的门槛。

看到的：
- 下行最大的一条流是字节的视频 CDN（`*.zjcdn.com`，约 9 MB）。它在规则里属于「字节跳动其它」，**不是「抖音」**：规则里的「抖音」这一项只收到 1.4 MiB，「字节跳动其它」收到 14.1 MiB。
- 下行第二大的流（约 8.6 MB，约 2 分钟）**没有名字**：它是抓包开始前就建立、被浏览器复用的长连接，没有 ClientHello，之前也没有查过它的 DNS。被动抓包读不到这类连接的名字；路线 B 里设备要先重连才能抓到握手，所以重连之后建立的连接都抓得到开头。
- 「持续下行」按默认门槛（50 KB/秒、30 秒、空格 15 秒）：只看「抖音」一项，**没有时段**；把「抖音」和「字节跳动其它」合起来，找到 14:47:10–14:48:15（65 秒），漏掉前半段；再把没名字的流也算上，找到 190 秒，正好是刷的那段（14:45:05–14:48:15）。放着不动的那段，任何门槛下都没有时段。
- 门槛放到 20 KB/秒，两个字节应用合起来是 140 秒；空格放到 30 秒是 190 秒。

结论（这份数据只能支持这些）：
1. 瓶颈是**名字**：长连接没名字、视频 CDN 不在「抖音」那一项里，比门槛的影响大。
2. 按单个应用统计会漏；同一家公司的应用（抖音、字节跳动其它）合起来看更接近实际。**已做**：规则里可以给应用写 `company`，「持续下行」按公司合起来算（自带规则只给抖音、TikTok、字节跳动其它写了「字节跳动」）。在这份数据上，合起来之后默认门槛找到 14:47:10–14:48:15（65 秒），和上面「抖音 + 字节跳动其它」那一行一致；没有名字的流占这台设备下行的 32%，不在统计里，报告会把这个比例写出来。
3. 默认的 50 KB/秒、15 秒空格在这一份里没有误报（放着不动的那段没有时段）；但只有一份、一种设备，不能说门槛合适。

另外这份数据暴露了一个 TCP 重组的问题并已修：每个方向只存前 1 MiB，存满后若还挑更小的段收，就会在中间留下「假缺口」，报告里写「缺 8.8 MB、抓包机漏抓了包」，其实一个包也没丢（tcpdump 报 0 dropped）。现在存满之后不再收任何段。

## 7. 隐私与范围

- 仓库是公开的：不放 WiFi 名、口令、MAC、真实抓包。示例一律用通用值。
- 只在自己的网络、自己的设备上用；他人设备（家人、访客）需要知情同意。
- 不爆破口令；纯 WPA3 不处理。
